# Roadmap: from WordPress to mafk-web

The full agenda for the site, what research found, the decisions still open,
and a proposed order of steps. **This is not a plan.** Each step below becomes
its own plan (`/plan`) once its open questions are answered.

## How to use this document

1. Discuss the **open questions** of the next step and record each answer in the
   [decision log](#decision-log) with a date.
2. When a step has no open questions left, start a plan for it. Point the plan at
   the step's section and the decisions it depends on.
3. When a step ships, mark it done in [Steps](#steps) and correct any finding
   that turned out wrong. Findings are dated, so re-check anything older than a
   few months before relying on it.

**Every step with anything visible is also a design task.** Its plan loads the
`frontend-design` skill (with `shadcn`) and follows its process: a short design
plan, reviewed against the brief before building, then a critique in Zen. The
brand tokens (Markaryd green, Inter) are shared with the app and stay fixed.
Step 3 carries the first real design pass: the public site's character.

  - The rest are empty stubs that redirect to Artportalen.

### The app's data (shared database)

- The app went live **2026-05-29**. Since then:
  - **238 observations** from 18 observers, covering 82 species.
  - 204 of the observations asked for a larm, and **154 have a photo**.
  - 238 `alerts` rows, 21 of them for observations that were later deleted.
- **Most reports are pins, not lokaler.** 211 of 238 observations have free
  coordinates, and only 27 use one of the **61** named `locations`. Alerts
  come from just 13 distinct lokaler.
- **Coordinates are not limited to the kommun.** They range over lat 53.3–56.7
  and lng −6.2–14.3, so at least one is from Ireland. "I kommunen" therefore
  needs a boundary check (see D7).
- `alerts` is a denormalized log: species, lokal and observer **names**,
  coordinates, count and `recipient_count`. It has **no image**. The photo is
  `observations.image_path` in the **private** bucket `user-uploads`: 170
  objects, 86 MB, about 0.5 MB each. The app shows photos through signed URLs.
- `species.rarity` (0 = rarest … 5 = most common) is set on 229 of 231 species.
- **Auth:** 46 users. Identities: email 19 (from the retired web app's magic
  link), Google 18, Apple 14. One admin since step 2.
- **Open issue in the app, not this site:** sign-up is open with
  `mailer_autoconfirm` on. Anyone can create an account with any email address,
  unconfirmed, and any signed-in account can read every member's profile
  (phone numbers included) and all observations. Raised 2026-09-19 and not
  changed, since it's the live app's configuration. Discuss with the club.
- **No PostGIS**, no `pg_trgm`, no `pg_cron`, no `pg_net`.
- **Members-only today.** Every existing table is readable by `authenticated`
  only, and the photo bucket is private. Nothing is readable anonymously, so
  anything the public site shows needs a server-side read (see D1).
- **Privacy policy (the app's, published on the WP site).** It says: *"Andra
  medlemmar i appen ser dina observationer inklusive art, plats, ev. foto och
  kommentar, samt ditt visningsnamn och – om du angett det – telefonnummer."*
  Members agreed to share with **members**. Publishing names, photos or exact
  places on the open web goes beyond that.
- **The larm pipeline could be reused from the web as it is.** The app inserts
  the observation (RLS: own rows) and then invokes `send-bird-alert`. It isn't
  wanted: the site never sends alerts (decided 2026-09-19).

### Artportalen

svalan.se is the old name. Everything is Artportalen now, run by SLU
Artdatabanken. Read from the SOS docs and source code (open source,
[biodiversitydata-se/SOS](https://github.com/biodiversitydata-se/SOS), release
2026.09.04). The API itself is untested, because it needs a key.

- **The official API is the Species Observation System (SOS).**
  - Base URL: `https://api.artdatabanken.se/species-observation-system/v1/`.
    Confirmed live: without a key it answers 401, "missing subscription key".
  - Access: a free account at
    [api-portal.artdatabanken.se](https://api-portal.artdatabanken.se/),
    subscribed to the product *"Species Observations – multiple data
    resources"*. Every request needs the key in the
    `Ocp-Apim-Subscription-Key` header. **Getting the key is a human step.**
  - The full OpenAPI spec is only downloadable from the portal after signing in.
  - SLU recommends calling it from a backend, never from the browser. That fits
    a Worker route with the key as a Worker secret.
- **`POST /Observations/TaxonAggregation` returns exactly what both lists
  need.** One row per taxon: `taxonId`, `observationCount`, `firstSighting` and
  `lastSighting`, for any search filter.
  - Årslista = the kommun's birds between 1 January and today, sorted by
    `firstSighting`.
  - Markarydslistan = the same with no date filter.
  - `take` omitted returns every taxon in one call (the paged form stops at
    1 000).
  - Filter: `geographics.areas: [{areaType: "Municipality", featureId: "767"}]`
    (kommunkod without the leading zero; the docs use Tranås `687` and Kronoberg
    `7`). Birds: `taxon: {ids: [4000104], includeUnderlyingTaxa: true}`
    (class Aves). Artportalen only: `dataProvider: {ids: [1]}`.
- **It returns ids, not names.** Names need a lookup:
  - a static bird-name map (taxon id → Swedish and scientific name) built once
    from Dyntaxa and kept in the repo;
  - an occasional lookup for an id the map doesn't know.
- **Fresh:** Artportalen is harvested incrementally every 5 minutes, so a report
  shows up in SOS within about 5 minutes.
- **Licence:** Artportalen's dataset is **CC0** (per GBIF). Credit "Källa:
  Artportalen, SLU Artdatabanken" anyway.
- **The kommun boundary is in the API too.**
  `GET /Areas/Municipality/767/Export` returns the kommun polygon, which is
  what D7 needs for Larmligan.
- **The catch: protected observations are hidden.**
  - The public index leaves out protected (skyddsklassade) observations.
  - Observations the reporter chose to blur have their coordinates diffused by
    100–1 000 m.
  - Protected data needs an SLU login (OAuth, scope
    `SOS.Observations.Protected`) and granted permission, which a club website
    won't get.
  - **Artportalen's own lists do include protected species.** The current
    Markarydslistan has Berguv, Pilgrimsfalk, Jaktfalk and Lappuggla. So an
    SOS-built list may lack a few species or show later first dates.
- **The baseline to test against** (Artportalen, fetched 2026-09-19):
  - Årslista 2026: **148 species**, latest addition Ljungpipare, 9 aug.
  - Markarydslistan: **229 species**, latest addition Rostgumpsvala,
    26 apr 2026.
- **Observatörsligan can't come from an aggregate.** Nothing aggregates by
  observer. It would mean pulling every bird observation in the kommun for the
  year (`Observations_SearchByCursor`, up to 2 million) and grouping by
  `occurrence.recordedBy`. It isn't on the agenda.
- Scraping artportalen.se is the fallback, and a poor one: it's fragile, and the
  user list loads by script.

## Cross-cutting decisions

These come before the features that depend on them. Each has a recommendation;
nothing is decided until it's in the log.

### D1 — What the public sees of the app's data

**Decided 2026-09-19:** only one administrator signs in on the web, and members
don't sign in at all (see D2). Everything the site shows from the app's data is
therefore **public**: the larm feed, the lokal map and Larmligan.

That conflicts with the app's privacy policy, which promises that only **other
members** see a member's observations, photos, name and place. Before any of it
goes public:

- **The club updates the privacy policy and tells the members** which larm
  details the website publishes. Reports made under the old promise need a
  decision too:
  - publish only reports made after the change, or
  - publish everything, but give members a way to opt out first.
- **Show the minimum.** Recommended public fields:

  | Field | Public? |
  |---|---|
  | Species, count, date, rarity | Yes |
  | Place | Lokal name. A pin is shown as the nearest lokal, or rounded to ~1 km, **never exact** |
  | Photo | Yes, if the policy says so. App photos are re-encoded with EXIF stripped, so they carry no hidden GPS; check any older upload first |
  | Observer's display name | Only if the policy says so; otherwise "en medlem" |
  | Comment (free text) | No |
  | Phone, user id, avatar | Never |

- **Protected species** (nesting raptors, owls and similar) never get a public
  place more precise than the kommun, or they are left out. The app has no
  sensitivity flag, and `rarity` measures something else, so this needs a list
  of its own, e.g. following Artportalen's protected species.
- **How it's served** (no change to the shared database):
  - Nothing there is readable anonymously, and the photo bucket is private. The
    Worker reads with a **secret key**, the site's first Worker secret.
  - The reading happens in one small module that maps rows to public DTOs. A
    test pins the DTO fields, so a phone number can't leak by accident.
  - Photos go through a Worker route (`/larm/bild/<id>`) instead of signed
    URLs. A signed URL would expose the storage path, which contains the
    member's user id, and would expire while a cached page still points at it.
  - Responses are cached for about a minute.
- **Open:**
  - the policy wording, and whether older reports are included;
  - whether observer names are shown (on the feed and in Larmligan);
  - the protected-species list;
  - how precise a pin may be.

### D2 — Admin sign-in

**Decided 2026-09-19, shipped in step 2:** exactly **one administrator** signs
in on the web, with **email and password**. There's no member login.

- The administrator is Jonas's existing app account
  (`yunus@edenmind.com`) with `profiles.is_admin = true`, granted by
  SQL. That flag is shared with the app, where it also allows creating lokaler
  (the `locations` insert policy). No second admin concept.
- Why password and not Google: the Google provider has no OAuth secret (it only
  serves the app's native ID tokens), so web Google sign-in would need a change
  to the shared auth config and the Google Cloud console. Password sign-in uses
  the email provider as it is, like `../mhf`: no email delivery, no callback URL,
  no auth config change.
- The password is set with `pnpm admin:password <email>`, run by the user in
  their own terminal, so it never passes through a chat or a log.
- The gate reads `profiles.is_admin` with the user's own session. The column is
  readable by signed-in users; only writing it is revoked. RLS on the site's
  tables (`private.is_admin()`) stays the real boundary.

### D3 — Where site media lives

This covers article images, page images and PDFs. It does **not** cover the
app's photos, which stay in `user-uploads`.

- **Recommendation:** a new **public Supabase Storage bucket** (`site-media`)
  owned by this repo.
  - Public read; writes need `private.is_admin()`.
  - Auth and RLS are already in place, and it needs no new Cloudflare binding.
  - Switch to **Cloudflare R2** (10 GB free, no egress fees) if measuring the WP
    library shows it would crowd the Supabase plan's storage or egress.
- **Measure first:** download the WP library, total its size, and check the
  Supabase plan's limits.
- Neither free tier resizes images at request time. Generate 2–3 widths at
  upload or import (browser-side in the admin, `sharp` in the import script)
  and serve them with `srcset`.
- **Open:** confirm the plan. Keep the PDFs (Cinclus archive) public?

### D4 — How published content renders

- **Rebuild-on-publish is ruled out by local-only shipping.** Prerendering
  articles would need a build and deploy on every publish, which means CI or
  Workers Builds deploying.
- **Recommendation: server-render DB content** (articles, pages, events) per
  request in the Worker, with a short `Cache-Control` so publishing shows up
  within a minute.
  - Sanitize HTML on **save**, not on render, to stay inside the Workers Free
    CPU budget (10 ms per request).
  - Pages that read nothing from the database (the 404, the legal pages) stay
    prerendered.
- **Routing consequence:** SSR paths must be in `run_worker_first`, because an
  asset miss serves the 404 page without calling the Worker (learned in step 1
  on `/admin`).
  - Either use fixed prefixes (`/artiklar/*`, `/kalender/*`, `/sidor/*`)
  - or route everything through the Worker and exclude static folders
    (`["/*", "!/_astro/*", …]`).

  Decide together with D6.
- **Watch:** Workers Free allows 100 000 requests a day, plenty for a club
  site. The $5 plan removes the CPU and request caps if needed.

### D5 — Editing and the HTML policy

"Generell html-redigering" means a WYSIWYG editor like WordPress's, plus an HTML
source view.

- **Recommendation: Tiptap** (headless ProseMirror, fits React and shadcn),
  storing **HTML**.
  - Sanitize server-side on save with an allowlist, since a stolen admin
    session must not be able to plant scripts.
  - Render with `set:html`.
  - Imported WP HTML goes through the same sanitizer.
- **Embeds** (Artportalen maps, YouTube) come in through an allowlist of iframe
  hosts, and each host is added to the CSP `frame-src`. Today's CSP has none, so
  it falls back to `default-src 'self'` and blocks every cross-origin iframe.
- **Open:** which embeds are needed (Artportalen and YouTube?). Are drafts,
  scheduled publishing and revision history wanted?

### D6 — URLs and redirects

- Old URLs must keep working: 353 posts at `/<slug>/`, pages at nested paths,
  inbound links, search results, and the app's legal links.
- **Recommendation:**
  - Clean new prefixes (e.g. `/artiklar/<slug>`, `/kalender/…`).
  - A generated `public/_redirects` with a 301 for every old URL. Workers static
    assets honour `_redirects` (up to 2 000 static rules; verify the limit when
    planning).
  - The two legal pages as **static `.astro` pages at their exact old URLs**,
    both forms. They change rarely, belong in version control, and then never
    depend on the database.
- **Open:** Swedish prefixes (`/artiklar`, `/kalender`, `/lokaler`)? Keep old
  slugs as the new slugs? (Recommended: yes.)

### D7 — What "i kommunen" means

Larmligan counts species seen **in Markaryds kommun**, but observations carry
free coordinates from anywhere.

- **Recommendation:** a point-in-polygon check against the kommun boundary,
  done in the Worker.
  - Use a simplified GeoJSON of kommun 0767 kept in the repo. The SOS API
    exports the exact polygon (`/Areas/Municipality/767/Export`); Lantmäteriet
    and SCB open data are alternatives.
  - Hundreds of points a year need no PostGIS. Enabling an extension on the
    shared database is avoidable.
  - Observations at a named lokal count if the lokal is inside.
- **Open:** count **observations** (every report) or only **alerts**? The alert
  log keeps `observer_name` after an account is deleted, and a public league
  must not show a deleted member. Recommendation: count from `observations`
  joined to `profiles`, so a deleted account drops out on its own.

## Features

Each lists the agenda item, the proposed shape, dependencies and open questions.

### F1 — Statiska sidor (pages)

- Admin-edited pages in a page tree (parent + order) that also drives the
  navigation menu. They cover about 20 of today's pages, migrated with F2's
  import. The Artportalen stubs become menu links.
- **New table:** `pages` (slug, parent, title, body HTML, status, order,
  timestamps).
- **Depends on:** D2, D4, D5, D6.
- **Open:** keep today's menu structure, or redesign it?

### F2 — Artiklar

- Articles (title, slug, excerpt, body, cover image, category, author name,
  published date, status), a public list with categories and paging, and the
  admin CRUD.
- **Dummy articles for now.** The WordPress import comes later (decided
  2026-09-19). Until then, build and test against a handful of dummy articles:
  - varied on purpose: with and without images, one long, several categories;
  - clearly marked (e.g. a slug prefix `exempel-`);
  - **deleted before the import**.
- **The import (later)** is a one-off, idempotent script (`scripts/wp-import/`,
  keyed on the WP id) that:
  - reads the public REST API. Drafts and private posts need an application
    password.
  - downloads own-host images into `site-media` in 2–3 widths;
  - rewrites `<img>` URLs;
  - sanitizes the HTML;
  - writes `_redirects`.

  A human runs it locally with a secret key in an uncommitted env file, first
  as a dry run.
- **Category cleanup:** 45 categories to a handful, mapped in a table the club
  signs off.
- **New tables:** `articles`, `categories` (or a text enum), maybe `media`.
- **Depends on:** D2–D6, and F1's editor.
- **Open, before the import:**
  - the category mapping;
  - hotlinked external images: try to copy them or drop them?
  - the 170 unattached media files: import or skip?
  - keep original publish dates and authors? (Recommended: yes.)

### F3 — Kalender (events)

- Events (title, start/end, all-day, place as free text or a `locations` lokal,
  description HTML, category, maybe a registration link). They replace both the
  "Program" posts and the hand-edited Årsprogram page.
- Public: upcoming list plus month view, and each event has a page.
- **Suggested extra: an iCal feed** (`/kalender.ics`) that anyone can subscribe
  to in their phone calendar. It's almost free to build.
- Admin CRUD.
- **New table:** `events`.
- **Depends on:** D2, D4, D5.
- **Open:**
  - recurring events? (Recommended: no; copy an event instead.)
  - import past program posts as events, or leave them as articles?
  - show events in the app later?

### F4 — Larm (public alert feed, with photos) — *viktig funktion*

**Decided 2026-09-19:** display only. The site never sends alerts.

- The app's alert feed on the public site: species, count, time, place,
  rarity, **photo**, and the observer if D1 allows. It has a detail view with a
  small map.
- Reads `alerts` and joins `observations.image_path` through `observation_id`
  (21 alerts have no observation left, so no photo).
- Everything goes through D1's public-data module, with the secret key,
  curated fields, and photos through a Worker route. It's all existing data,
  with **no migration**.
- Keyset paging, since Supabase caps responses at 1 000 rows.
- **Depends on:** D1, including the club's privacy-policy update, which must go
  out **before** this ships.
- **Open:** D1's questions.

### F5 — Lokaler (map)

- A public map of lokaler with their larm history, like the app's Lokaler
  screen. It shows the 61 named lokaler and the alert pins at D1's precision,
  and each lokal lists its alerts.
- A React island (`client:visible`) with Leaflet or MapLibre. Tiles from
  OpenStreetMap or Lantmäteriet's open topographic map. Tile hosts go into the
  CSP.
- **Depends on:** D1 and F4's public-data module.
- **Open:**
  - show pins, or only named lokaler (27 of 238 reports use one)?
  - cluster the pins?
  - should the 9 WP lokal pages (Köphultasjö, Hammarsjön …) become lokal
    detail pages?

### F6 — Larmligan

- A public leaderboard of distinct species per member **in the kommun** this
  year, with earlier years selectable. It's computed in the Worker (see D7).
- Names follow D1. If observer names aren't public, a league makes little sense,
  so D1 decides whether this feature exists at all.
- **Depends on:** D1, D7, and F4's public-data module.
- **Open:** see D7. Tie-break by who reached the count first? Show each
  member's species list?

### F7 — Årslista and Kommunlista (Artportalen)

These are today's redirects: this year's species list for the kommun, and
*Markarydslistan* (every species ever recorded in the kommun, with the first
date).

- **Phase A, at launch (parity):** links or redirects to the same Artportalen
  pages, with the year computed. That removes the New Year chore.
- **Phase B, native:**
  - an SSR route that makes **one** `TaxonAggregation` call per list (kommun
    `767`, birds, Artportalen), maps the ids to names, and sorts by first
    sighting;
  - caches the answer (Cache API, refreshed in the background every few hours)
    and renders it in the site's design, with "Källa: Artportalen";
  - the key is a Worker secret.
- **The spike comes first, about an hour once there's a key.** Build both
  lists from SOS and compare them with the baseline (148 and 229 species).
  Measure the response time. The outcome decides phase B:
  - **They match, or only differ by protected species:** go native. A missing
    protected species can be noted ("exkl. skyddsklassade fynd") or added by
    hand.
  - **They differ a lot:** keep linking to Artportalen, the authoritative list.
- **Observatörsligan** (Artportalen's user top list) exists today but isn't on
  the agenda. Keep it as a link, or drop it now that Larmligan exists?
- **Depends on:** nothing internal. It can happen at any point.

### F8 — Admin area

- One administrator (D2). Every step adds its screens to `/admin`. The shell
  (navigation, sign-in gate, layout) is part of the sign-in step.
